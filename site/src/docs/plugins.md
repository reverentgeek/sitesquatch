title: "Built-in plugins"
---
- **`ssqch/image`:** `imagePlugin(options)` turns every local `<img>` in HTML output into a `<picture>`. Options: `formats` (`avif`, `webp`, `jpeg`, `png`, `auto`), `widths`, `defaultAttributes`, `outputDir`, `urlPath`, `webpQuality`, `avifQuality`, `avifEffort`, `jpegQuality`, `minimumThreshold`, `prune`, `hashCache`, `linkedImages` and `cacheDir` (where images are encoded and kept, default `.cache/ssqch/img`; see [Keep the image cache between builds](deploying.md#keep-the-image-cache-between-builds)). Images are encoded with [sharp](https://sharp.pixelplumbing.com), and the quality options are its own numbers, whole numbers from 1 to 100: `webpQuality` 75, `avifQuality` 41 and `jpegQuality` 89 (mozjpeg) by default, and `avifEffort` 2 (0 is fastest, 9 is slowest with the smallest files). A number out of range fails the build and says what to use. PNGs are written at zlib's level 6. `[ssqch] Encoded ...` lines come as each image's files are done, while pages go on rendering; the build waits for every file before the link checker, the other plugins' files, `afterBuild` hooks and the summary. Images are encoded as many at once as there are cores, each on one thread, so a file's bytes don't depend on the machine (set `UV_THREADPOOL_SIZE` to change how many threads the pool has). A file that can't be made after a page that points at it was written (sharp failing on a source that read well, a full disk) fails the build with an `images` error that names the source and the pages, rather than publish markup for a file that isn't there; a source ssqch can't decode is found before any page points at it, and is a warning that leaves its tag as written. On an `<img>`, `ssqch:widths="300,600"` picks that image's widths, a plain `width` attribute pins it to one width, and `ssqch:ignore` leaves it alone. `ssqch:preload` is for the image that's the page's largest paint (a banner): a `<link rel="preload" as="image">` with its `imagesrcset` and `imagesizes` goes in `<head>` before the first stylesheet, for the first of `formats`, and the image loads eagerly with `fetchpriority="high"` (`sizes="auto"` only works for lazy images, so `auto` is left out of its `sizes`). Images with a color profile other than sRGB (Display P3, Adobe RGB) are converted to sRGB first, so their colors stay true. A link to a local image (`<a href="/photos/big.jpg">`, the click-to-enlarge pattern) is pointed at a generated copy in the image's own format, at its own width capped at the largest of `widths`, so the link works without publishing the source file; `ssqch:ignore` on the `<a>`, or `linkedImages: false`, leaves links alone. `image(src, { widths, formats })` makes one image's files with the same settings and cache, returning `{ webp: [{ url, width, height, srcset, sourceType, ... }] }`; with `"auto"` in `formats`, the files are under `auto` too, next to the format it became (`png`). Its files are named after a hash of the source; `name` gives them a name and folder of your own, for URLs other things link to (`image("logos/acme.png", { widths: [200], name: "/assets/sponsors/acme" })` writes `/assets/sponsors/acme-200.webp`, and a name without a leading `/` is inside the image folder). Data files can call it even without the plugin. `imageUrl(src, { width, format })` is one generated copy, for URLs outside an `<img>` (`og:image`, JSON-LD, a feed): `{{ imageUrl(site.logo, { width: 1200 }).url }}` gives `{ url, width, height, type, format }`, at most `width` pixels wide (`"auto"`, the default, is the original's) in `format` (default `"auto"`, the source's own, which every reader can show). `src` is a site path, from the input folder, the way an `<img src>` starting with `/` is, and a remote URL comes back as `{ url }`. It's a template function on every site, and a named export of `ssqch/image` for data files.
- **`ssqch/minify`:** `minifyPlugin(options)` minifies HTML output, after the image transform. `minify(html, options)` does the same for a string. Options: `collapseWhitespace`, `removeComments`, `shortDoctype` and `shortenAttributes` (all `true` by default), and, off by default as html-minifier's are, `css` (each page's `<style>` elements compressed, as `minifyCss` does), `xml` (the whitespace between tags out of `.xml`, `.rss` and `.atom` files, such as feeds and sitemaps, but not inside text, CDATA or comments) and `json` (`.json` and `.webmanifest` files without spaces). `minifyCss(css)` compresses CSS text with ssqch's Sass, as a compressed stylesheet is written (`.a { color: #ffffff; }` becomes `.a{color:#fff}`), for CSS a template inlines: `filters: { minifyCss }`. It reads the text as plain CSS, so Sass's own syntax, and CSS it can't read (native CSS nesting among it), is an error naming the line; with `css: true`, such a `<style>` stays as it is and the build warns once for the page. Each text is compressed once and kept, so a stylesheet inlined in every page costs one compression. `shortenAttributes` drops the values of boolean attributes (`defer="defer"` becomes `defer`) and whitespace that doesn't matter in `class`, `srcset`, `sizes`, URL attributes and the viewport `<meta>`, whose numbers it writes as html-minifier-terser does (`initial-scale=1.0` becomes `initial-scale=1`). The minifier is ssqch's own, built into the package as WebAssembly, and it minifies the ReverentGeek blog's 169 pages in about 0.1 s. Its output isn't byte for byte [html-minifier-terser](https://github.com/terser/html-minifier-terser)'s with `collapseWhitespace`, `removeComments`, `useShortDoctype` and `collapseBooleanAttributes`, in two ways: it keeps each attribute's quotes as written (`class='a'`, `href=x`), where html-minifier-terser writes every value in double quotes, and it leaves an unclosed element as it is (`<p>one<p>two`), where html-minifier-terser closes it. It has none of html-minifier-terser's other options (`removeOptionalTags`, `removeAttributeQuotes`, `sortAttributes`, `decodeEntities`, `minifyCSS`, `minifyJS`): a site that needs those bytes runs that package as a transform instead, and `ssqch diff` (not `--exact`) reads the two minifiers' output as the same where only quotes differ.
- **`ssqch/rss`:** `rssPlugin()` adds the filters `getNewestCollectionItemDate`, `dateToRfc3339`, `dateToRfc822`, `rssDate` and `rssLastUpdatedDate` (the Eleventy RSS plugin's first names, as aliases: they work, and say once that they're `dateToRfc3339` and `getNewestCollectionItemDate | dateToRfc3339`), `absoluteUrl`, `htmlToAbsoluteUrls` and `feedHtml`. They're also named exports, for your own code. Under a [`base`](deploying.md#serving-a-site-under-a-path), the filters put it in front of a URL from the site's root that doesn't have it yet (`absoluteUrl(post.url, site.url)` is `https://example.com/repo/posts/pine/`), and so do `htmlToAbsoluteUrls` and `feedHtml` for every URL in the HTML; the named exports resolve a URL as `new URL(url, address)` does, so call `withBase` first there. `feedHtml(post.templateContent, absolutePostUrl)` is a post's HTML ready for a feed: a feed's HTML never goes through the image plugin, so each local `<img src>` is pointed at one generated copy (a single URL, not a `<picture>` or `srcset`, which many readers drop), a link to a local image at the copy a page's link gets, `loading`, `decoding`, `sizes`, `srcset`, `fetchpriority` and `ssqch:*` attributes go, and every URL is made absolute. Options, as a third argument: `width` (default 1200, never wider than the original; an `<img width>` that's smaller wins) and `format` (default `"auto"`, the source's). `feedHtml` makes the copies with the image plugin, so the config needs `imagePlugin()` as well; without it the build fails with `the image processor isn't set up`.
- **`ssqch/assets`:** `assetsPlugin({ files })` fingerprints CSS and JS for long-lived caching. Templates link the plain paths (`<link rel="stylesheet" href="/assets/index.css">`). In a production build, each listed file in the output folder (written there by your CSS or JS tool before `ssqch build`) is renamed to `index.<hash>.css`, older fingerprinted copies are deleted, and every `href` and `src` in the HTML that points at it is rewritten, keeping any query string. `ssqch serve` leaves the plain paths alone, unless the plain file isn't there but the last production build left a fingerprinted copy: then pages link to that copy (with a warning), so serving after a build without running your CSS and JS watchers still has styles. A listed file that's missing fails a production build. `assetUrl("/assets/index.css")` returns the URL to use, for places outside an `href` or `src`. Imports in inline module scripts are rewritten too (`<script type="module">import { setup } from "/assets/pco.js"</script>`, and `import("/assets/pco.js")` with a plain string), and a listed file can be a passthrough copy: it's copied into the output before it's fingerprinted. `url()` references inside CSS and imports inside JavaScript files aren't rewritten. Options: `files` (URL paths, required), `fingerprint` (`true` or `false`; on for production builds by default) and `integrity` (add `integrity="sha384-..."` to the `<link>` and `<script>` elements that load a fingerprinted file; default `false`).
- **`ssqch/links`:** `linksPlugin(options)` checks the built site's internal links after each build. Every `href` (on `a`, `link` and `area`), `src` (images, scripts, iframes, media), `srcset` and `imagesrcset` URL has to point at something in the output, and a `#fragment` has to match an `id` on the page it points to. URLs outside attributes are checked too, when they're on the site (from its root, or absolute on its address): `<meta>` values that are URLs (`og:image`, `og:url`, `twitter:image`), strings in `application/ld+json` blocks (without their `#fragment`, which names a thing there), and in `.xml` output (feeds, the sitemap), URLs in attributes and in elements like `<loc>` and `<id>`, including the escaped HTML of a feed entry's content. That's where an image URL the image plugin never saw shows up: a feed's `<img>` pointing at a source file that isn't published. The site's address is the `url` option, or the one `sitemap.xml` uses; links to it (`https://example.com/about/`, `http` or `https`) are checked like links from the root. Other external links aren't checked, and neither are paths a Netlify `_redirects` file in the output covers. Broken links fail production builds, listing each page and link (the first 20, then `... and N more (--verbose lists them all)`; `--verbose` lists every one), and are warnings in `ssqch serve`. One that's nearly right says what it probably meant: `/about/ -> /contactt/ (not found; did you mean /contact/?)`, and the same for an `id`. Options: `anchors` (check `#fragments`; default `true`), `ignore` (URL path prefixes to skip, like `["/downloads/"]`), `fail` (`true` or `false`; production builds only by default) and `url` (the site's address, like `"https://example.com"`; default: the address in `sitemap.xml`).
- **`ssqch/sass`:** `sassPlugin({ files: { "src/scss": "/css" } })` compiles Sass with [grass](https://github.com/connorskees/grass), built into the package as WebAssembly, so there's no Dart Sass to install. grass writes a few things differently from Dart Sass; a site that needs Dart Sass's exact output can run the `sass` package from `beforeBuild` instead (`{ run: "sass src/scss:dist/css" }`). A folder compiles every `.scss` and `.sass` file in it that doesn't start with `_`, keeping their paths; a file (`{ "src/app.scss": "/app.css" }`) compiles to the path given. The CSS is written at the start of each build, so `ssqch/assets` can fingerprint it and the link checker sees it, and `ssqch serve` rebuilds when a source changes. Options: `files` (required), `style` (`"compressed"` for production builds and `"expanded"` otherwise, by default), `loadPaths`, and `charset`: `false` leaves out what grass (as Dart Sass) starts CSS with when it has a character outside ASCII, a byte order mark when compressed and `@charset "UTF-8";` when expanded, so the file starts as a Jekyll site's did (jekyll-sass-converter takes the mark out). An import that names its extension (`@import "primer-core/index.scss"`) is found in the load paths too, as Dart Sass finds it, and a stylesheet that starts with Jekyll's front matter (`---` lines) compiles, the lines left blank. (Yes, that makes it Sassquatch.)
- **`ssqch/sitemap`:** `sitemapPlugin({ url: "https://example.com" })` writes `sitemap.xml` listing every HTML page with its absolute URL and its date as `<lastmod>`. Left out: pages with `sitemap: false` in their data, 404 pages, pages 2 and on of a list split into pages (pagination with a `size` over 1; a page per tag is still listed), and URLs matching `exclude` globs (`["/tags/**"]`). Options: `url` (the site's address, required: a sitemap lists whole addresses, and search engines read only those, so a build without one stops and asks for it; jekyll-sitemap wrote paths from the root instead), `exclude`, `lastmod` (default `true`), `output` (default `"/sitemap.xml"`), `paginated` (list every page of a split list) and `alternates`, a page's translations as hreflang links: a function that gets each page (`url`, `inputPath`, `outputPath`, `date`, `data`) and returns `[{ hreflang: "fr", href: "/fr/guide/" }]`, the page itself included (`x-default` too, if you have one), or nothing. An `href` from the site's root gets the address and `base` in front, and the sitemap gets the `xhtml` namespace only when a page has some: `alternates: (page) => page.data.translations?.map((t) => ({ hreflang: t.lang, href: t.url }))`. It's called at once, so work the translations out in data or a collection first.
- **`ssqch/elements`:** `elementsPlugin()` is interactivity without a framework. A custom element is a tag with a hyphen (`<like-button>`) and a script that defines it. Put `like-button.js` in `src/elements/` (and `like-button.css` next to it, if it has styles), write the tag in any page or layout, and that page gets the script and the stylesheet; pages without the tag get neither, so a page with no elements loads no JavaScript. What's inside the tag is the fallback a visitor sees before the script runs, or without JavaScript: `<like-button><a href="/likes/">3 likes</a></like-button>`. `ssqch:load` on a tag says when its script loads: `eager` (with the page, the default), `idle` (when the browser has a quiet moment) or `visible` (when the element scrolls into view), which is the "islands" idea without a framework to run it. The whole folder is copied to `/elements/`, so elements can import shared modules (a file without a hyphen in its name isn't an element). Options: `dir` (default: `elements` in the input folder, which has to exist), `url` (default `/elements/`) and `load` (`eager`, `idle` or `visible`: the default for tags without `ssqch:load`; any other value is an error that says so). The [`islands` example](https://github.com/reverentgeek/sitesquatch/tree/main/examples/sites/islands/) has three small elements.

- **`ssqch/llms`:** `llmsPlugin({ url: "https://example.com", description: "Hikes and the gear for them." })` writes the site for language models, as [llmstxt.org](https://llmstxt.org) describes it: `/llms.txt` lists the site's pages (each one's title, a link to its Markdown and its `description`), under a `##` heading for each of the site's top folders (`/guide/...` is "Guide"; the top's pages are "Pages"), and each of those pages gets a Markdown copy beside its URL as llms.txt's v2 proposal has it (`/guide/intro.html` is `/guide/intro.md`; a URL without a file name gets `index.md`, so `/guide/intro/` is `/guide/intro/index.md` and `/` is `/index.md`). A copy is what the page says: a Markdown page's copy is its Markdown after its template engine ran (`{{ site.title }}` is the title, a `{% for %}` is the list it wrote), without its front matter, its `<script>` and `<style>` blocks, or pictures with `alt=""` (decoration), and with its title on top when only the front matter had it; any other page's copy (a home page in Jinja) is its `<article>`, or else its `<main>` or `<body>`, as Markdown (headings, paragraphs, lists, links, code, quotes, tables and described pictures; navigation, forms, scripts and anything `hidden` are left out). Links in a copy are whole addresses (with `url`), and a link to a page that has a copy goes to the copy, a relative `.md` link to another page's file included (`[Install](install.md)`). `/llms-full.txt` has the heading, then every copy in one file, each after a `url:` line. A page whose front matter says `llms: false` is left out. The plugin adds one template function, `markdownCopy(page.url)`: the URL of the page's copy, or `""` when it has none, for the layout to link it (a build adds no markup of its own): `{% if markdownCopy(page.url) %}<link rel="alternate" type="text/markdown" href="{{ markdownCopy(page.url) }}">{% endif %}`. Options: `title` (the `#` heading; default `site.title` in the site's data, or the home page's title), `description` (a `>` line under it), `details` (Markdown after that, in both files: what a model should know first), `url` (the site's address, for whole links; without it, links are from the site's root), `exclude` (URL globs, like `["/drafts/**"]`; 404 pages are always left out), `copies` (default `true`; `false` links `llms.txt` to the pages instead), `full` (default `true`), `section` (a function that gets each page and returns its section's name; sections come in the order of their first page) and `sort` (a function that compares two pages, as `Array.prototype.sort` takes it; default by URL). vitepress-plugin-llms does this for VitePress sites.

> [!NOTE]
> **Not released yet.** This ships with the next version of ssqch: `ssqch/llms` as described above. In 0.12.0, a copy is the page's source file (template code and all), only Markdown pages are listed, and `hint: true` writes a hidden `<div>` in place of `markdownCopy`.

- **`ssqch/robots`:** `robotsPlugin({ ai: { training: false } })` writes `/robots.txt`: everyone's group (`disallow`, URL paths no crawler should read), a group with `Disallow: /` for each kind of AI crawler that's turned off (`ai`: `training`, `search` and `fetch`, each `true` by default), and the `Sitemap:` line with `sitemapPlugin()`'s address (`sitemap: false` leaves it out, a string is another address). [Posted signs](robots.md) lists the crawlers of each kind and the links a layout writes for agents.

> [!NOTE]
> **Not released yet.** This ships with the next version of ssqch: `ssqch/robots`.

- **`ssqch/vue`:** `vuePlugin(options)` renders the Vue components a site's pages use, at build time, with the site's own Vite, `@vitejs/plugin-vue` and Vue (`npm install -D vite @vitejs/plugin-vue vue`; ssqch doesn't bundle them, and says so if they're missing). With pnpm, which keeps a VitePress site's vite and @vitejs/plugin-vue beside `vitepress` rather than in the site's `node_modules`, they're found there. Vue renders with its production build in a production build and its development build while serving (`NODE_ENV` follows ssqch's env unless you set it). A page's `<script setup>` imports name them, as VitePress's pages do (`import ApiIndex from './ApiIndex.vue'`, then `<ApiIndex />` in the page), and `components` names the ones every page can use (`{ VueSchoolLink: ".vitepress/theme/components/VueSchoolLink.vue" }`, VitePress's `app.component()`). Each tag a page has (and no template in `_includes/components/`, which comes first) becomes the HTML Vue's server renderer writes for it: its attributes are its props, and a binding is read as Vue reads it in the page, with the page's front matter (`frontmatter`, `$frontmatter`), `params` (a dynamic route's, from its URL: `[partnerId].md` written as `/partners/vehikl.html`), `page` (VitePress's `useData().page`) and the `data` of each VitePress loader its `<script setup>` imports (`import { data } from './errors.data'`; the loader's `load()` runs once a build, through Vite, with `__dirname`), and what's between its tags is its default slot, with the components inside it rendered first (a layout component that holds the page works). On a VitePress site (one with a `.vitepress` folder, or `vitepress: true`), components that import from `"vitepress"` get a stand-in (with `current`, its page's state, for a wrapper that renders the site's theme: the VitePress trailhead's "Keeping your VitePress theme") for `useData()` (the page's front matter, title and route, and the config's `themeConfig`), `useRoute()`, `withBase()` and `inBrowser`, and `@theme/` is the theme's folder. `hydrate` runs each component in the browser too, as an island: `"load"`, `"idle"` or `"visible"` (when it scrolls into view) wraps its HTML in `<ssqch-vue>` and adds one script to the pages that have one, `/assets/vue/islands.js`, which loads only the components on the page; default `false`, HTML only. `css` is where the components' styles go (default `"/assets/vue.css"`, for your layout to link; `false` for none), and the fonts and images they point at go where Vite put them (`/assets/inter-x.woff2`, after `base`); the site's `public/` isn't copied (that's `passthrough`'s), `root` is Vite's root (default the input folder, so scope ids are VitePress's), and `vite` adds Vite options (`resolve.alias`, `plugins`). The components build in `.cache/ssqch/vue/` before each build; while serving, an edit that's only to pages keeps the last one. A VitePress loader named like ssqch's data (`api/api.data.ts`) goes in `ignore`, which `ssqch scout` drafts.
- **`ssqch/redirects`:** `redirectsPlugin(options)` keeps old URLs working. A page lists its old URLs in front matter (`aliases: [/2019/pine-cones/, /pine.html]`), and the `redirects` option adds others (`{ "/feed/": "/feed.xml" }`, where the new URL can be on another site). Each old URL gets a small page that sends visitors on (a meta refresh, a canonical link and `noindex`), and with `netlify: true`, a `/old  /new  301` line is appended to `_redirects`, after any lines your own `_redirects` template writes, and [`linksPlugin()`](#) honors those lines. An old URL that's another page's URL is an error. For redirect pages in your own markup, add `_includes/hooks/redirect.*` (any engine): it gets `redirect.from` and `redirect.to` with the site's global data. Options: `pages` (default `true`), `netlify` (default `false`) and `redirects`.
